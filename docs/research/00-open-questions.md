## Техрешение этапа 1 (закрываем по ходу)
- [x] Имя и форма заголовка ключа → зафиксированы в contracts
      (`MERCHANT_KEY_HEADER`, `merchantKeyHeaderValue`, `merchantKeyFrom` в
      `packages/contracts/src/api.ts`); гейтвей и SDK импортируют один
      источник, drift ловит тест api.test.ts
- [x] Сборка публикуемых пакетов → есть. `tsc` собирает исходный SDK мерчанта и
      его пакет контрактов в `dist` — JS плюс декларации рядом; бандлер не
      заводили, потому что исходники и так импортируют друг друга через
      `.js`-спецификаторы, которые `tsc` переносит как есть. Внутри монорепо
      ничего не поменялось: `exports` по-прежнему указывает на `src`, а на
      сборку его подменяет `publishConfig` в момент упаковки, — правка видна
      без компиляции. `bin` объявлен там же, поэтому установленная команда проверки SDK
      стартует. Проверяет это `pnpm outside`: удаляет `dist`, пакует тарболы
      (сборку делает `prepack`, так что путь тот же, что у релиза), ставит их
      npm-ом в каталог вне репозитория и гоняет там импорт и `verify` —
      с заведомо неполной карточкой как контролем. Перед первой публикацией эта
      же проверка компилирует импорт в чужом strict TypeScript-проекте с
      `skipLibCheck: false`, стандартными Web API Node 24 и без ambient-пакетов
      из рабочего дерева. Публикацией управляет Changesets, public-доступ задан
      и пакет `0.1.0` выпускается тегом `sdk-v0.1.0` через отдельный workflow
- [x] Работает ли `verify` по ключу, без файлов → нет, и это решение, а не
      недоделка. Такой проверке нечего проверять: карточка попадает в
      `list_merchant_cards` только пройдя `CardSchema` на публикации, а
      `checkCard` гоняет ту же схему, — то есть проверка по построению всегда
