# Кастодиальный спектр: техническая заметка

2026-08-25, трек A. Вопрос владельца продукта: можем ли на этой же
архитектуре позже стать custodial (только техника, без рынка/регуляторики).

## Ответ: архитектура custody-агностична по построению

Деньги упоминаются в системе в одном месте — поле `payTo` 402-ответа,
которое мы выдаём **per-request**. Агенту/протоколу/фасилитатору/каталогу
безразлично, чей адрес. Кастодиальность = вопрос маршрутизации значения
одного поля + бэк-офис после денег. Исключение — атомарный сплит из точки 2
и эскроу Commerce Payments Protocol из точки 3: им нужна схема
`auth-capture`, то есть другая подпись покупателя, а не другое значение
`payTo` (`38-service-commission.md`).

## Спектр (все точки, кроме атомарного сплита и эскроу Commerce Payments Protocol, достижимы без изменения протокольной стороны)

1. **Direct (сейчас)**: payTo = кошелёк мерчанта. Ноль кастодии.
2. **Split-контракт**: payTo = контракт «мерчанту его доля, нам комиссия».
   При `exact` деление не атомарно: USDC просто зачисляется на контракт, а
   делит его вторая транзакция; на открытых проверенных контрактах в рамках
   стандартного x402 атомарно делит только схема `auth-capture`, где payTo
   остаётся кошельком мерчанта (разбор — `38-service-commission.md`).
   Держим только свои фи. (= техническое решение монетизации.)
3. **Escrow-контракт** (программируемая кастодия): контракт с правилами
   release/refund (подтверждение фулфилмента / срыв SLA). Свой эскроу с
   отложенным выпуском можно поставить на payTo, как сплит; эскроу Commerce
   Payments Protocol — нет: в `auth-capture` payTo остаётся кошельком
   мерчанта, а эскроу получает разрешение покупателя отдельно.
   Деньги держит код, не наши ключи. Прецедент готов: **Commerce Payments
   Protocol** (Coinbase+Shopify, open source, Base, authorize/capture) —
   адаптировать, не изобретать.
4. **Omnibus custodial**: наш кошелёк + двойной леджер + payout-движок
   (батчи, идемпотентность, реконсиляция) + key management (MPC/CDP Server
   Wallets). Классический PSP-бэк-офис; протокол не меняется.

## Ключевая связка с режимами выдачи

Кастодиальность — **per-order политика, не глобальная позиция**:
`sync` → direct мерчанту; `async`/`confirm-first` → escrow с авто-рефандом
по дедлайну. Закрывает слабую стенку AX («рефанд исполняет мерчант») кодом
вместо обещания.

## Единственная настоящая техзадача перехода: атрибуция

`transferWithAuthorization` не несёт memo → входящие на общий адрес не
привязать к заказу. Решение: **per-order детерминированные адреса**
(CREATE2 vault, адрес = f(orderId)); дороже по газу, реконсиляция железная.

## Что делаем сейчас (дёшево), чтобы дверь была открыта

- [ ] payTo в ядре — routing-слой (функция заказ→адрес), не строка конфига.
- [ ] Леджер заказов с первого дня (нужен и для async/квитанций); custodial
      позже = добавить денежные ноги к существующему леджеру. Эталон
      взрослого леджера — платёжная машина Freeland (см. 03).
