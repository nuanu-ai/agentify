# Ответ на ревью PR #215, 28 октября

Это отчёт для владельца продукта. Локальные проверки исправлений завершены;
итоговый CI и сквозная проверка TEST ещё ожидаются. TEST не переключён. Предыдущий коммит `a8ab8d59` прошёл CI, но ревью нашло
существенные пробелы в реализации и проверках. Старый зелёный прогон не служит
приёмкой исправленной версии.

| Замечание | Что подтверждено и как исправляем |
| --- | --- |
| 1. Мусорный платёж создаёт заказ | Подтверждено. Проверка теперь предшествует записи. Заказ, владелец, разрешение на платёж, задания и событие создания записываются одной транзакцией. Неуспешная проверка ничего из этого не оставляет. Проверки ограничены для всех цен, включая фиксированные. |
| 2. Бесплатные вопросы мешают оплаченным посылкам | Подтверждён общий пул. Созданы отдельные ресурсы; бесплатная очистка не занимает оплаченные корзины. Перед получением заказа воркер резервирует нужную пару, поэтому ожидание мест не тратит попытку. Уточнение: десять сбоев до создания заказа в WooCommerce сами по себе не останавливают продавца; такие сбои не входят в этот счётчик. |
| 3. Сомнительные корзины заканчиваются навсегда | Подтверждено. По решению владельца от 28 октября сомнительную корзину больше не используем; новую создаём автоматически не чаще раза за десять минут на магазин. Бюджет сохраняется между перезапусками и переподключениями. |
| 4. Подпись из каталога получает окончательный отказ | Подтверждено. Платёж без штампа проходит обычную валидацию покупки и получает новый 402 с настоящей ценой. До новой подписи нет проверки платежа, заказа или списания. Это стандартный вход из каталога, без поддержки старого `order_id`. |
| 5. Повтор после срока советует купить ещё раз, пока первый запрос может пройти | Подтверждено. Одна граница принятия сериализует цену. Пока первый запрос может завершиться, повтор получает нейтральный ответ с советом сохранить и повторять ту же покупку. Потеря соединения с блокировкой не позволяет старому проверяющему позже записать или списать платёж. |
| 6. Реализация спрятана в слиянии | Подтверждено. История собирается от `main` на `b6382b27`: отдельно запрет кэширования, идентификация сборки и сайт продавца, затем целое изменение работы с неоплаченными ценами. Перед заменой ветки итоговое дерево сверяется с проверенной версией. |

## Инженерные решения и причины

Проверку подлинности выполняем до записи, а финансовые действия после коммита.
Обычной блокировки процесса недостаточно: после потери её соединения старый
вызов может продолжить работу. Поэтому запись использует ту же транзакцию,
которая держит блокировку цены. Реальная проверка PostgreSQL уже обрывает это
соединение и подтверждает отсутствие поздней записи, события, разрешения и
списания; предусмотрена и успешная следующая покупка.

Для платежей выбраны один проверяемый запрос на продавца и четыре на процесс.
На канал развёрнут один процесс шлюза; масштабирование потребует отдельного
решения об общих ограничителях и маршрутизации вопросов. Это
оставляет соединения базы для обычной работы и не позволяет одному продавцу
занять все места. Это начальные внутренние границы, не замер пропускной
способности. Место удерживается до завершения реального вызова: у используемого
HTTP-клиента есть прерывающий срок 30 секунд, у обращений к сети десять секунд.
Одного таймера, забывающего продолжающийся запрос, недостаточно.

Не ограничиваем подпись длиной обычного кошелька. Пустые байты могут быть
корректны для контрактного кошелька; отсутствующие, нечитаемые и некорректные
байты отсекаются до внешнего вызова. Некоторые внешне правильные подписи всё
равно требуют ограниченной внешней проверки. Текст отказа одинаков до и после
оплаты, чтобы через него нельзя было узнать состояние чужого заказа.

Условия карточки, продавца и получателя перепроверяются при атомарном принятии,
включая изменения во время проверки. Срок цены по-прежнему оценивается по
приходу полного платёжного запроса, а не по скорости проверяющего сервиса.
Полный адрес фиксируется под блокировкой владельца; оплаченный заказ использует
сохранённые финансовые условия и прежние правила восстановления.

В каждой полосе WooCommerce восемь корзин: четыре обработчика могут одновременно
считать два адреса для проверки налогов. Число обработчиков и публичный SDK не
расширены. При нехватке безопасных оплаченных корзин общий опрос временно ждёт;
это может задержать и другие задания этого коннектора, зато не расходует
попытки уже оплаченного заказа. Более сложный отбор по типам заданий отложен.

Сохраняются только ограниченные сведения о ресурсах: права первого создания,
бюджет замен, владелец и зашифрованные безопасные токены. Это позволяет не
обнулять лимит после перезапуска и не создавать корзины заново без нужды.
Чужой старый владелец проверяется до расшифровки и ничего не меняет. Учётные
данные и кэши разных подключений не объединяются вместе с корзинами. Каждая
новая, восстановленная или обновлённая подпись корзины подтверждает владение
её сессией в той же записи магазина до следующего изменения корзины. Ротация
токена не позволяет двум местам владеть одной сессией после перезапуска.

При стандартных двух днях жизни гостевой сессии получается пул 16 плюс примерно
288 замен, то есть около 304 неистёкших сессий на магазин. Это не обещание
количества физических строк: удаление истёкших записей зависит от WooCommerce,
а изменённый срок сессии меняет расчёт. На восстановление нескольких корзин
может потребоваться несколько десятиминутных интервалов.

Класс неоплаченных невладельческих заказов больше не возникает, поэтому удалены
его очистка через 30 дней, отдельный сегмент и вспомогательные пути создания.
Принятые заказы и неизвестные финансовые исходы не удаляются. Тесты хранения
сохраняют проверки блокировок, отката и финансовой истории на реальных путях
принятия, а не добавляют производственный вход для тестовых данных.

Клиент, уже подписавший каталожный 402, должен обработать полученный новый 402.
Установленный `@x402/fetch` автоматически обрабатывает один 402 на вызов;
следующий ответ 402 в той же цепочке он не подписывает снова. Не обещаем
универсальную работу всех внешних клиентов; проверяем сам HTTP-протокол и
обычную покупку с полноценным телом.

Для ошибок восстановления корзин сначала получены воспроизведения: истёкшая
неочищенная корзина, завершение старого владельца со старым ключом шифрования
и повтор платной сессии новой бесплатной корзиной после перезапуска. Проверки
сохраняют финансовую историю и не создают производственный вход для фикстур.

Отдельная проба реального `woo.nuanu.ai` 28 октября выполнила 20 анонимных
запросов за 7,249 секунды без заказов и платежей. Корзинная часть бесплатного
расчёта вместе с очисткой заняла 2,827 секунды, после перезапуска 2,061 секунды.
Параллельная оплаченная полоса заняла 2,388 и 2,029 секунды. После восстановления
из PostgreSQL новые корзины не открывались, платные и бесплатные сессии
оставались разными, все использованные корзины подтверждены пустыми.

Эта проба исключает закрытые чтения товара и настроек, проверку базового налога,
курс валют и транспорт воркера. Она не доказывает срок полного ответа цены или
пропускную способность. Предсказание хотя бы одного превышения четырёх секунд
для корзинной части не подтвердилось. Исходные результаты и сценарий сохранены
в частном архиве владельца `Agentify-acceptance/2026-10-28-pr215-5li11mfu`;
временная база и ключ пробы удалены. Отпечаток исходников в отчёте пробы
предшествует лишь удалению неиспользуемых экспортов без изменения поведения.
