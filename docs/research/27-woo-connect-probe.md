# Проба: подключение WooCommerce без плагина

2026-09-14. Стенд и пробы — `spikes/woo/` на ветке `spike/woo-connect`
(запушена; стенд пересобирается с нуля одной командой, WordPress 7.1 +
WooCommerce 11.1.0). Три вопроса были названы до старта, вердикты — по
выводу скриптовых проб; негативный контроль переворачивает все три в
FAIL, так что зелёное измеряет поведение, а не себя.

## Вердикты

1. **wc-auth работает — PASS.** Механизм 2015 года жив целиком: authorize →
   Approve → редирект с `success=1` → отдельный серверный POST на наш
   callback с `consumer_key`/`consumer_secret`/`key_permissions=read_write`.
   Выданные ключи реально аутентифицируют против `wc/v3` (проверено и по
   https, и по http). У мерчанта ключ виден в его же настройках как
   «Coinslot - API».
2. **Витрина читается без плагина — PASS.** `GET /wp-json/wc/store/v1/products`
   без авторизации и куки → 200, все посеянные товары, из коробки.
3. **Оплаченный заказ снаружи — PASS.** `POST wc/v3/orders` с
   `set_paid: true` → 201, `status=processing`, дата оплаты стоит; четыре
   независимых свидетеля согласны (ответ REST, WP-CLI, сырое хранилище,
   экран админки).

Схема «Connect-кнопка → чтение витрины → создание заказа», записанная в
`06-prior-art-web2.md`, подтверждена на живом самохостном магазине.

## Ловушки, найденные пробами

- **Plain permalinks ломают Connect молча**: authorize-URL не даёт 404, а
  редиректит на главную страницу магазина с 200. Мерчант жмёт Connect и
  оказывается у себя на витрине без какой-либо ошибки. Connect-флоу обязан
  делать префлайт: GET authorize-URL и убедиться, что пришёл экран выдачи
  доступа, а не главная.
- **Пять обязательных параметров**: `app_name`, `user_id`, `return_url`,
  `callback_url`, `scope` — без любого из них 401. Approve — это GET по
  ссылке с nonce, не POST формы.
- **Callback — только SSL и только порты 80/443/8080**: `http://`-callback
  отвергается словами «needs to be over SSL», бессхемный молча дополняется
  до `https://`. Наш приёмник ключей должен жить на 443 с настоящим
  сертификатом — это не артефакт стенда.
- **Выбор REST-аутентификации зависит от `is_ssl()` магазина**: по https —
  Basic; по http Basic отвергается сообщением про права («you cannot list
  resources»), которое не называет настоящую причину, и требуется подпись
  OAuth 1.0a. Оба пути проверены одними и теми же ключами.
- **Цены в двух API в разных единицах**: Store API отдаёт минорные единицы
  строкой (`"12000"` при `currency_minor_unit: 2`), `wc/v3` — десятичные.
  Конвертер каталога, читающий `price` без учёта масштаба, молча ошибается
  в сто раз.
- **Создание заказа шлёт письма**: мерчанту («New order») и покупателю
  («order has been received»), из запроса это не подавить. Прежде чем
  создавать заказы на чьём-то живом магазине, нужно продуктовое решение:
  что стоит в заказе как email покупателя и кому летят письма.

## Что не проверено

- HPOS (новое хранилище заказов) на стенде выключено — WP-CLI-установка
  ставит легаси. Через REST это неразличимо; важно только тому, кто полезет
  в БД напрямую (мы не лезем).
- Живой магазин с реальной почтой, реальным TLS и чужими данными: стенд —
  лаборатория. Два послабления стенда (частные IP, самоподписанный CA)
  включаются флагом и записаны как артефакты лаборатории.

## Следующий шаг, если канал открывается

Connect-экран в кабинете (пять параметров, префлайт пермалинков, callback
на 443, `success=1` — подсказка, а не факт: факт — серверный POST) и
конвертер «товар Store API → карточка» с учётом минорных единиц и нашей
двери (длинные описания и кириллические имена будут отказаны — отказ
показывается мерчанту честно). Оба — продуктовая поверхность; открытие
канала — слово Дмитрия.
